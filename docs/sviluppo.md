# Guida allo sviluppo

Convenzioni e procedure ricorrenti. Il quadro d'insieme e' in [`architecture.md`](architecture.md), le scelte di
progetto in [`decisions.md`](decisions.md), l'avvio in [`README`](../README.md).

## Principi

- **Monolite modulare**: ogni sotto-package diretto di `com.fcusumano.sam` e' un modulo Spring Modulith
  (`shared`, `ccnl`, `anagrafica`, `cedolini`, `calcoli`, `segnalazioni`, `web`). Le dipendenze ammesse sono
  dichiarate in `package-info.java` (`@ApplicationModule(allowedDependencies = ...)`) e non devono creare cicli.
- **API pubblica = package radice del modulo** (interfacce, record, enum, eventi). Tutto cio' che sta nei
  sotto-package (`domain`, `application`, `adapter`, `config`) e' interno: un altro modulo non lo puo' usare.
  Unica eccezione `shared`, modulo OPEN.
- **Comunicazione tra moduli** solo tramite API pubbliche ed eventi, mai leggendo o scrivendo le tabelle altrui.
- **Verifiche automatiche** a ogni `./mvnw -B verify`: `ModularityTests` (confini, cicli, package interni) e
  `ArchitectureTests` (dominio puro, jOOQ, SDK Anthropic e PDFBox solo negli adapter, ogni modulo solo le proprie
  tabelle). Se uno dei due fallisce, va corretto il codice, non il test.
- **Stile**: Java 25 idiomatico (record, sealed, pattern matching, `switch` esaustivi), iniezione da costruttore,
  classi interne package-private, `BigDecimal` per importi e quantita' (mai `float`/`double`), termini di dominio e
  commenti in italiano, sobri. Niente TODO o codice provvisorio nei rami principali.
- **Privacy**: solo dati inventati in test, fixture e mock; nei log a livello INFO solo id e tipi di errore (mai
  codici fiscali, nominativi, importi, nomi file caricati o password).

## Struttura esagonale di un modulo

```
<modulo>/
├── package-info.java      @ApplicationModule
├── *.java                 API pubblica (porte di ingresso, record, eventi)
├── domain/                logica pura: nessuna dipendenza da Spring, jOOQ, SDK Anthropic
├── application/           servizi che implementano l'API, porte di uscita (interfacce), listener di eventi
├── adapter/persistence/   implementazioni jOOQ delle porte di persistenza
├── adapter/<altro>/       altri adapter (es. cedolini.adapter.locale, .ai, .pdf, .fixture)
└── config/                @ConfigurationProperties e @Bean che collegano il dominio a Spring
```

- La logica (regole, calcoli, normalizzazioni) sta in `domain` ed e' testata con test unitari puri, senza Spring.
- `application` orchestra: transazioni, chiamate alle porte, pubblicazione degli eventi.
- Le classi di `domain` non possono avere annotazioni Spring: si registrano come bean in `config` (metodi `@Bean`).
- Le proprieta' di configurazione sono record `@ConfigurationProperties` del modulo che le usa, con default
  (`@DefaultValue`) coerenti con `application.yml`; i parametri di calcolo (aliquote, tassi, divisori) non si
  cablano mai nel codice.

## Database: tabelle e changelog

Ogni modulo possiede le proprie tabelle e i propri changelog Liquibase in
`backend/src/main/resources/db/changelog/changes/`, inclusi in ordine alfabetico da `db.changelog-master.yaml`:

| Intervallo | Modulo         |
|------------|----------------|
| `0xx`      | `shared`       |
| `1xx`      | `anagrafica`   |
| `2xx`      | `ccnl`         |
| `3xx`      | `cedolini`     |
| `4xx`      | `calcoli`      |
| `5xx`      | `segnalazioni` |

Regole:

1. **Formatted SQL** (`--liquibase formatted sql`, `--changeset sam:<numero>-<descrizione>`), un file per
   evolutiva, con il prossimo numero libero dell'intervallo del modulo (es. `240-ccnl-nuovi-contratti.sql`).
2. **Mai modificare un changeset gia' rilasciato**: ogni cambiamento e' un nuovo changeset (`ALTER`, `UPDATE`, ...).
3. **DDL compatibili PostgreSQL** (H2 gira in `MODE=PostgreSQL`): `BIGINT GENERATED BY DEFAULT AS IDENTITY`,
   `NUMERIC(15,5)` per importi e quantita', `BYTEA`, `TEXT`, `BOOLEAN`, `DATE`, `TIMESTAMP WITH TIME ZONE`; niente
   sintassi specifica di H2.
4. Ogni tabella di dominio ha `workspace_id` con FK verso `workspace`; ogni colonna FK ha il suo indice (basta che
   sia la prima colonna di una chiave primaria o di un vincolo UNIQUE); le tabelle derivate e figlie usano
   `ON DELETE CASCADE` verso il dato da cui dipendono.
   - **Chiavi composte**: una tabella che descrive un'entita' identificata da piu' colonne usa quelle colonne come
     chiave primaria, senza un id artificiale. Esempio: `caricamento_pdf` e `caricamento_attribuzione` hanno chiave
     `(workspace_id, hash_contenuto)` (un file = un contenuto), che garantisce "al piu' una riga per file" senza
     controlli applicativi e copre anche l'indice della FK verso `workspace`.
   - **FK verso la tabella di un altro modulo**: ammessa solo con `ON DELETE CASCADE` verso il dato da cui la riga
     dipende (`riepilogo_rapporto`, `segnalazione`, `caricamento_attribuzione.rapporto_id` verso `rapporto_lavoro`):
     il database ripulisce le righe quando il dato sparisce, senza che un modulo scriva le tabelle di un altro.
5. **Nuova tabella** => aggiungerla in `ArchitectureTests.TABELLE_PER_MODULO` sotto il modulo proprietario
   (`ogniTabellaHaUnModuloProprietario` fallisce finche' non e' assegnata) e documentarla in `architecture.md`.
6. Il codice jOOQ si rigenera da solo in build (`generate-sources`, package `com.fcusumano.sam.shared.db.jooq`):
   dopo una modifica allo schema basta `./mvnw -B generate-sources` (o la build completa). Solo gli adapter di
   persistenza del modulo proprietario usano le classi della tabella.
7. Nessun dato bancario in nessuna tabella.

## Eventi e ricalcolo

- Gli eventi sono record nell'API pubblica del modulo che li pubblica (`cedolini.CedolinoAcquisito`,
  `cedolini.CedolinoEliminato`, `cedolini.CaricamentiInErroreModificati`, `anagrafica.CcnlRapportoModificato`,
  `anagrafica.RapportoLavoroEliminato`).
- Si pubblicano con `ApplicationEventPublisher` **dentro** la transazione che modifica i dati.
- Si ascoltano con `@EventListener` (consegna **sincrona**, stessa transazione): niente `@TransactionalEventListener`,
  `@ApplicationModuleListener` o `@Async`, e niente event publication registry. Un errore nel listener annulla
  l'intera operazione: i dati derivati non possono restare disallineati.
- I ricalcoli sono **da zero**, deterministici e idempotenti: si cancellano i dati derivati del rapporto e si
  reinseriscono a partire da cedolini, anagrafica e CCNL. Ricalcolare due volte deve dare lo stesso risultato,
  e un test lo deve verificare.
- Un nuovo modulo con dati derivati da un rapporto ascolta `CedolinoAcquisito`, `CedolinoEliminato` e
  `CcnlRapportoModificato` e ricalcola il rapporto indicato. Se i suoi dati dipendono anche dalle mensilita' a cui
  l'utente ha associato un file in errore (oggi solo le segnalazioni), ascolta anche `CaricamentiInErroreModificati`
  e ricalcola ogni rapporto dell'evento.
- Lo stato che i listener leggono va aggiornato **prima** di pubblicare l'evento: nell'acquisizione il caricamento
  diventa ACQUISITO e PDF conservato e associazione del file vengono eliminati prima di `CedolinoAcquisito`.
- Una transazione annullata annulla anche i ricalcoli dei listener: la verifica dell'inserimento a mano sfrutta
  questo per eseguire l'acquisizione vera e annullarla. Un listener con effetti fuori dal database (file, chiamate
  esterne, cache) romperebbe questa garanzia: non va introdotto.

## Aggiungere una regola di segnalazione

Principio vincolante: **ogni segnalazione deve essere veritiera**. Meglio non segnalare che segnalare il falso: con
dati insufficienti, ambigui o con una causa nota (anticipo TFR, trasferimento a fondo pensione, cambio d'anno per i
progressivi, assorbimento del superminimo al rinnovo, liquidazione di fine rapporto) la regola non segnala.

1. **Tipo**: se serve un tipo nuovo, aggiungerlo a `segnalazioni.TipoSegnalazione` e all'enum `tipo` dello schema
   `Segnalazione` in `docs/openapi.yaml`, poi rigenerare il client TypeScript (vedi sotto). Titolo e descrizione
   arrivano gia' pronti dal backend: il frontend non va toccato.
2. **Regola**: una classe in `segnalazioni.domain` che implementa `RegolaSegnalazione`:
   - `codice()`: codice stabile (di norma il nome del tipo);
   - `valuta(ContestoRapporto)`: restituisce le `SegnalazioneRilevata` (tipo, gravita', titolo, descrizione,
     evidenze con i cedolini e i valori coinvolti) oppure una lista vuota. Java puro, nessuna dipendenza da Spring.
3. **Registrazione**: come bean nel modulo segnalazioni (metodo `@Bean` in `segnalazioni.config.SegnalazioniConfiguration`,
   perche' la classe di dominio non puo' essere annotata; eventuali parametri in `SegnalazioniProperties`,
   `salary-manager.segnalazioni.*`): `MotoreSegnalazioni` valuta tutte le regole registrate a ogni ricalcolo.
4. **Test unitario** dedicato in `src/test/java/com/fcusumano/sam/segnalazioni/domain/`, con almeno: caso che
   segnala (con evidenze corrette), casi con causa nota che non segnalano, dati insufficienti che non segnalano.
5. **Verifica sullo scenario demo** (fixture inventate): la regola non deve produrre falsi positivi sui casi gia'
   coperti (rinnovo CCNL con assorbimento, anticipo TFR, fine rapporto, tredicesima nel cedolino di dicembre, ...).

## Aggiungere o correggere un CCNL

La tabella `ccnl` e' un dato di riferimento globale, popolato da changelog del modulo `ccnl` (intervallo `2xx`).

1. Nuovo changeset (es. `240-ccnl-<nome>.sql`) con `INSERT INTO ccnl (...)` o `UPDATE` per correzioni:
   - `codice` (maiuscolo, stabile), `descrizione`;
   - `mensilita` (13 o 14), `mese_quattordicesima`, `periodicita_scatti_mesi`, `max_scatti`: **solo se noti con
     certezza**, altrimenti `NULL` con una `note_verifica` (con regole scatti ignote non si stimano scatti e non si
     segnalano scatti mancanti);
   - `parole_chiave`: frasi separate da `|`, confrontate come **parole intere** sul testo normalizzato (minuscolo,
     senza accenti e punteggiatura); elencare le forme flesse ("metalmeccanico|metalmeccanici|..."), evitare sigle
     brevi o ambigue;
   - `parole_escluse`: frasi che escludono il CCNL (es. "artigianato" per un contratto industriale, "dirigenti");
   - `codice_cnel` (es. `C018`): solo se verificato sull'archivio CNEL; se stampato sul cedolino deve essere coerente
     con le parole chiave, altrimenti non si riconosce nulla.
2. Test in `RiconoscitoreCcnlTest` (e, se serve, `CatalogoCcnlIntegrationTest`) con testi stampati inventati: il
   riconoscimento atteso e i casi che **non** devono essere riconosciuti (contratti affini, artigianato, PMI, ...).
   Il riconoscimento restituisce un CCNL solo se univoco.
3. Il frontend legge l'elenco da `GET /api/v1/ccnl`: nessuna modifica necessaria. I rapporti senza CCNL riconosciuto
   restano "da indicare"; la scelta dell'utente non viene mai sovrascritta dall'estrazione.

## Contratto REST e client TypeScript

- Il contratto di riferimento e' [`openapi.yaml`](openapi.yaml): ogni modifica alle API parte da li'.
- Il backend lo implementa nel modulo `web` (`web.api`: controller e DTO record, proprieta' JSON in camelCase
  italiano); springdoc espone la versione generata su `/v3/api-docs`, da tenere allineata al file.
- Il client del frontend e' generato con `openapi-typescript`:

  ```bash
  cd frontend
  npm run gen:api       # rigenera src/api/schema.d.ts da ../docs/openapi.yaml (file versionato)
  npm run typecheck     # mostra i punti del frontend da adeguare
  ```

  `schema.d.ts` non si modifica a mano; va committato insieme a `openapi.yaml`. Se cambia un enum (es. un nuovo
  tipo di segnalazione) aggiornare anche i dati simulati in `frontend/src/mocks/`.
- **Errori campo per campo**: per i corpi strutturati (oggi l'associazione di un file in errore e l'inserimento a
  mano) il modulo che valida solleva `shared.DatiNonValidiException` con una lista di `ErroreCampo(campo, messaggio)`;
  `web.error.GestoreErrori` la traduce in 400 `richiesta-non-valida` con la proprieta' `errori` di `Problema`
  (`detail` = il messaggio dell'unico errore oppure "N campi da correggere"). `campo` e' il percorso nello schema
  della richiesta (`totali.netto`, `voci[3].descrizione`, `anno`), `null` per un errore generale; il frontend lo
  converte nel percorso del modulo (`voci.3.descrizione`). Negli altri 400 `errori` e' assente.

## Lettori dei cedolini e fixture

- I tre lettori (`locale`, `claude`, `fixture`, scelti con `salary-manager.lettore` / `SAM_LETTORE`) implementano la
  porta `LettoreCedolini` e producono il JSON dello schema `backend/src/main/resources/prompts/cedolino-schema-v1.json`,
  che passa sempre da `InterpreteRispostaEstrazione` (normalizzazione e validazione comuni); il record Java
  corrispondente e' `CedolinoEstratto`. Un cambiamento allo schema va riflesso nel record, nel validatore, nel prompt
  di Claude (`estrazione-cedolino-v1.md`), in `CedolinoLetto.json` del lettore locale e nelle fixture.
- L'inserimento a mano e' il quarto produttore dello stesso JSON (`modello_estrazione` = `inserimento-manuale-1`) e
  il suo modulo deve rispecchiare tutti i campi del lettore: un cambiamento allo schema va riflesso anche nel percorso
  manuale. Backend: `cedolini.CedolinoManuale`, `ValidazioneCedolinoManuale` (normalizzazione e limiti),
  `JsonCedolinoManuale` (scrive il JSON v1), `web.api.dto.CedolinoManualeDto` con `Mappatura` e lo schema
  `CedolinoManuale` in `docs/openapi.yaml` (poi `npm run gen:api`). Frontend: `ValoriCedolinoManuale`, `valoriVuoti`,
  `richiestaDa`, `daCedolinoRiferimento` e le validazioni in `hooks/useCedolinoManuale.ts`, le sezioni del modulo
  (`components/SezioniCedolinoManuale.tsx`, `TabellaVociModificabile.tsx`, `TabellaRateiModificabile.tsx`), le
  etichette `testi.campoCedolino` in `i18n/it.ts` e il backend simulato `mocks/inserimentoManuale.ts`.
  `JsonCedolinoManualeTest` valida il JSON prodotto contro lo schema (tutte le proprieta' sono obbligatorie): un campo
  nuovo non scritto dal percorso manuale lo fa fallire, ma il modulo e il DTO vanno aggiornati a mano.
- Il lettore Claude non deve dipendere dal testo estratto localmente dal PDF (le scansioni non ne hanno): riceve il
  PDF come documento. Il lettore locale invece legge solo il testo: un PDF senza testo e' un errore, non un caso da
  indovinare.
- Nuova fixture (solo dati inventati): `fixtures/cedolini/<nome>.json` nel formato dello structured output e
  `fixtures/pdf/<nome>.pdf` con la riga `Fixture: <nome>`; descriverla in `fixtures/README.md`. Le fixture usate
  solo dai test vanno in `src/test/resources/fixtures/`.

## Lettore locale: aggiungere un layout

Il lettore locale (`cedolini.adapter.locale`) prova i layout di `LettoreLocaleCedolini.LAYOUT` in ordine e usa il
primo che riconosce il documento. Ogni layout e' una classe che implementa `LayoutCedolino`. Principio vincolante:
**non indovinare**. Un campo che non si trova resta `null`; un layout che non si riconosce con certezza produce un
errore che suggerisce Claude, mai un cedolino con dati sbagliati.

1. **Studio del layout** (solo in locale, con i cedolini in `samples/`, mai nel repository): servono le etichette
   stampate e le loro posizioni. `TestoPdf.leggi(byte[])` restituisce il `DocumentoTesto`: pagine, righe
   (`Pagina.righe()`, con la linea di base `y` dall'alto) e parole con `x0`/`x1`. Per esaminarlo si scrive un test
   temporaneo **non committato** che stampa le righe di un campione; le parole che non sono etichette vanno
   mascherate (per esempio sostituendo lettere e cifre con `X` e `9`), cosi' nemmeno l'output contiene dati personali.
2. **Classe del layout** (`Layout<Nome>`, package-private, `final`):
   - `id()`: identificativo stabile in minuscolo con trattini, finisce nel modello registrato
     (`lettore-locale-1/<id>`); `nome()`: nome leggibile per i messaggi;
   - `riconosce(DocumentoTesto)`: **stretto**, su poche etichette caratteristiche che nessun altro layout stampa,
     cercate nel testo compatto (`documento.compatto()`: maiuscolo, senza spazi);
   - `leggi(DocumentoTesto)`: compila un `CedolinoLetto`. Le posizioni sono **relative alle etichette**
     (`Zone.etichetta`, `Pagina.prima`, `Zone.aDestra`, `Zone.sotto`, `Zone.valoriSotto`, `Zone.perInizio` per le
     colonne) cosi' margini e formati di pagina diversi non contano; solo per i moduli prestampati, le cui etichette
     non sono nel testo, si usano coordinate del foglio scalate sulla pagina (vedi `LayoutModuloM39320`). Valori con
     `Valori` (importi, date, mesi, codici fiscali), periodo con `Periodo`; voci con `CedolinoLetto.voce` (categoria da
     `Classificazione.categoria`), ratei come `CedolinoLetto.Rateo` (tipo e unita' da `Classificazione`).
   - Sezioni attese e non trovate: `CedolinoLetto.etichettaMancante`; controlli interni non superati (somme, TFR):
     `controlloFallito` (`controllaSomme` confronta le voci con i totali stampati). Entrambi riducono la confidenza e
     diventano avvisi: devono contenere **solo nomi**, mai valori.
   - Mai leggere dati bancari (IBAN, ABI, CAB, conto), mai loggare valori letti.
3. **Registrazione**: aggiungere il layout a `LettoreLocaleCedolini.LAYOUT`. L'ordine conta solo se due layout
   potessero riconoscere lo stesso documento, cosa da evitare con `riconosce` stretto.
4. **Test con dati inventati**: un PDF sintetico che riproduce etichette e posizioni del layout, generato in memoria
   con `PdfSintetico` (testo in coordinate dall'alto, allineamento a destra degli importi, pagine di formato
   diverso), in un metodo di `CedoliniSintetici` (nomi, codici fiscali e aziende inventati: "Mario Rossi",
   `RSSMRA80A01H501U`, "Alfa Software S.r.l."). In `LettoreLocaleCedoliniTest` un test campo per campo (periodo,
   anagrafica, totali, voci con le categorie, ratei, TFR, avvisi, confidenza) piu' i casi particolari del layout
   (tredicesima, fine rapporto, grafiche alternative). Mai PDF reali, nemmeno anonimizzati.
5. **Misura sui campioni** (locale, senza rete):

   ```bash
   cd backend
   ./mvnw test -Dgroups=campioni -Dsam.test.excludedGroups=none
   ```

   `MisuraCampioniLocaleTest` legge tutti i PDF di `SAM_SAMPLES_DIR` (default `../samples`; piu' cartelle separate
   da `:`, su Windows da `;`) e stampa per ogni file solo numero, layout, esito, conteggi e controlli di coerenza, poi
   una tabella aggregata, i campi chiave non trovati e il confronto dei mesi consecutivi. Il nuovo layout e' pronto
   quando tutti i suoi campioni sono letti con netto, somme, ratei e TFR coerenti e i campi chiave non trovati sono
   solo quelli che il cedolino non stampa.
6. **Documentazione**: tabella dei layout nel README (sezione "Lettori dei cedolini") e, se la scelta non e' ovvia,
   una decisione in `decisions.md`. Se cambiano le regole di lettura in modo da rendere utile una rilettura dei
   cedolini gia' caricati, aumentare `LettoreLocaleCedolini.VERSIONE`.

## Test end-to-end (facoltativi)

La suite Playwright in `frontend/e2e/` percorre il flusso completo nel browser contro lo stack vero: avvia da sola
il backend in modalita' demo (`SAM_LETTORE=fixture`, database H2 nuovo in una cartella temporanea) sulla porta
18080 e Vite sulla 15173, poi carica i PDF di `backend/src/main/resources/fixtures/pdf/`.

```bash
cd frontend
npx playwright install chromium     # una volta: scarica il browser
npm run e2e                         # SAM_E2E_BACKEND_PORT / SAM_E2E_FRONTEND_PORT per cambiare porte
```

Non fa parte di `./mvnw verify` ne' di `npm test`/`npm run build`: va eseguita prima di consegnare modifiche
all'interfaccia o al flusso di caricamento. I test sono in sequenza e costruiscono i dati passo dopo passo; un nuovo
scenario si aggiunge in coda o in un file separato con un proprio database. Con `SAM_E2E_SCREENSHOT_DIR` la suite
salva gli screenshot desktop e mobile del flusso, utili per controllare l'aspetto delle pagine. Altre variabili in
[`frontend/README.md`](../frontend/README.md#test-end-to-end).

## Messaggi e testi

- I testi dell'interfaccia stanno in `frontend/src/i18n/it.ts`; i messaggi che il backend restituisce all'utente
  (errori di caricamento, problem details) sono in italiano corretto, con le lettere accentate.
- Log e commenti nel codice usano l'apostrofo al posto dell'accento (`e'`, `piu'`) e non contengono mai dati
  personali, nomi di file caricati o password.
- I messaggi di `ErroreCampo` (errori campo per campo) dicono cosa correggere senza mai ripetere il valore inviato
  ("Codice fiscale non valido: controlla i 16 caratteri", non il codice): finiscono nella risposta e possono finire
  nei log del browser o di un proxy. I testi della segnalazione `CEDOLINO_IN_ERRORE` riportano mensilita' e motivo
  dell'errore, mai il nome del file caricato.

## Prima di consegnare

```bash
cd backend && ./mvnw -B verify
cd frontend && npm run lint && npm run typecheck && npm run format:check && npm test && npm run build
cd frontend && npm run e2e          # facoltativo, per modifiche a interfaccia o caricamento
cd backend && ./mvnw test -Dgroups=campioni -Dsam.test.excludedGroups=none   # per modifiche al lettore locale
```

Aggiornare `docs/decisions.md` per le scelte non ovvie e `docs/architecture.md` se cambiano moduli, tabelle,
eventi o flussi.
